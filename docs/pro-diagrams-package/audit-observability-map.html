Audit And Observability Map

A professional map for proving what happened without leaking sensitive data: event sources, sanitization, logs, metrics, traces, audit records, alerts, dashboards, retention, ownership, and incident review.

Purpose

Audit and observability are related, but not identical. Observability helps operators understand system health. Audit helps reviewers prove who did what, when, and why.

The pro move is to design both deliberately so logs do not become a second database of secrets.

Golden rule Record enough to prove the decision and diagnose the system, never enough to reconstruct private data, secrets, raw payloads, or token-real mappings.

1. End-To-End Audit Flow

Source

Decision Or Event

Request, auth decision, policy denial, write, export, admin action, failure.

Shape

Structured Event

Use IDs, categories, counts, reason codes, and component names.

Sanitize

Redaction Gate

Remove secrets, raw payloads, tokens, PII/PHI, stack traces, and unsafe values.

Route

Telemetry Router

Send appropriate fields to logs, metrics, traces, audit, and alerting.

Store

Protected Storage

Retain audit and telemetry with access control and retention rules.

Detect

Alert Rules

Trigger on abuse patterns, failures, policy bypass indicators, and anomalies.

Review

Investigation

Dashboards, reports, incident timelines, compliance evidence, postmortems.

2. Telemetry Types

Logs

What Happened

Discrete events, errors, decisions, denials, state transitions, admin actions.

Metrics

How Much / How Fast

Counts, durations, rates, queue depths, denial spikes, latency, error ratios.

Traces

Where Time Went

Request path across services with spans, timing, dependencies, and correlation IDs.

Audit

Who Did What

Actor, action, resource category, decision, reason, time, source, safe evidence.

Alerts

What Needs Attention

Threshold, anomaly, security signal, incident trigger, paging or ticket routing.

Reports

What To Prove

Compliance summaries, access reviews, abuse reports, postmortem evidence.

Every event should be joinable without exposing sensitive content.

7. Audit Store Structure

Schema

Structured Fields

Time, actor, action, component, decision, reason, request, resource category.

Payload

Safe Evidence

Counts, categories, validation codes, policy version, redaction summary.

Protection

Access Control

Restrict read access, separate admin roles, review access logs.

Integrity

Tamper Evidence

Append-only storage, hash chain, external sink, write-once retention where needed.

Retention

Lifecycle

Keep based on legal, compliance, and operational policy; delete on schedule.

10. Review Checklist

Question Pass Criteria
Can every high-risk action be reconstructed from audit?Actor, action, resource category, decision, reason, time, and request correlation exist.
Can audit records leak sensitive data?Sanitization tests cover raw payloads, secrets, IDs, stack traces, and token maps.
Are alerts tied to response actions?Each high-severity alert has an owner and runbook.
Are logs correlated across services?Request ID and trace ID appear across gateway, API, worker, and audit paths.
Are audit and telemetry retained appropriately?Retention windows, access control, and deletion policies are documented.
Can telemetry survive incidents?Audit write failures are detected, and critical evidence is stored outside the failing service.
